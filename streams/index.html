Streams

KafkaClient.streams runs a Kafka Streams program. Each running instance is one member of the application, and the application can mix xkafka members with Java Kafka Streams instances running the same program. Members share the work and take it over from each other as they start and stop.

Streams applications need brokers of Kafka 4.2 or newer.

// Count each page's views across all users, and write every new count to a topic
import cats.data.NonEmptyList
import cats.effect.IO

import xkafka.*
import xkafka.streams.*

val user  = Serde.utf8[IO]
val page  = Serde.utf8[IO]
val views = Serde.long[IO]

val program =
  for
    input    <- Topic.from("page-views").liftTo[IO]
    output   <- Topic.from("views-per-page").liftTo[IO]
    pipeline  = KStream(Named("page-views"), input, user, page)
                  // Key each view by its page, through a repartition topic
                  .groupBy(Repartition("views-by-page"), page, page)((_, viewed) => viewed)
                  .count(Named("count-views"), Store("views-per-page"))  // Keep each page's count in a store
                  .toStream(Named("view-counts"))                        // Turn each change to a count into a record
                  .to(Named("write-view-counts"), output, page, views)   // Write each change to the output topic
    topology <- Topology.of(pipeline).liftTo[IO]                         // Check the program for problems
    client   <- ClientSettings.from(NonEmptyList.one("localhost:9092")).liftTo[IO]
    id       <- ApplicationId.from("page-view-counter").liftTo[IO]
    settings <- StreamsSettings.from(client, id).liftTo[IO]
    _        <- KafkaClient[IO].streams(settings, topology).use(_.run)  // Join the application and keep processing
  yield ()

The input topic holds a record for each page a user views, keyed by the user. The program counts the views of each page, and writes every new count to views-per-page, keyed by the page.

Acquiring the resource joins the application and starts processing. run waits while the application runs, and fails with the error that stops it. Releasing the resource commits the member's work, hands it back to the application, and leaves, waiting at most the settings' closeTimeout, 30 seconds by default. Running a program covers guarantees, concurrency and stores.

Programs

A program is a Topology of pipelines. A pipeline starts by reading a topic, as a KStream or as a KTable (see Tables), and is built with:

  • filter, filterNot, map, mapValues, flatMap, flatMapValues, selectKey and peek;
  • evalFilter, evalMap and evalMapValues, which run an effect;
  • filterRecord, mapRecord, mapRecordValue and others like them, which also see each record's time and headers (see Steps that see the whole record);
  • repartition, which sends records through a repartition topic you name, with as many partitions as you choose (see Choosing partitions);
  • groupByKey or groupBy, followed by count, reduce or aggregate into a named Store. This gives a KTable, and its toStream is every change to it. A table can be grouped too (see Grouping a table), and several groups can be folded together (see Folding streams together);
  • toTable, which keeps each key's latest value as a KTable;
  • join, leftJoin and outerJoin, which combine it with a table or a stream, and join and leftJoin with a global table, and joinOnForeignKey and leftJoinOnForeignKey, which join a table with the rows its values name (see Joins);
  • fork, forkMerge, merge, split and into, which send records down several paths or bring them together (see Branching);
  • to, which ends a path at an output topic, or foreach and print, which end it by acting on each record or printing it.

A KStream can read several topics as one source, given as a NonEmptyList, as Java's stream can given several topics. A record is read with the same serdes whichever topic it came from, and each deserializer is told that topic. A topic listed twice is read once. Partitions with the same number are processed together, so to keep a key's records together for grouping or joining, give the topics the same number of partitions.

Each topic and store is read and written with a Serde, which pairs a serializer and a deserializer of one type, since a streams application both reads and writes. Serde(serializer, deserializer) makes one. .option turns a serde into one of Options, which reads and writes a null as None, so a None value is written as a tombstone. Serde.utf8, Serde.long and Serde.bytes write the same bytes as Java's Serdes.String(), Serdes.Long() and Serdes.ByteArray().

Every step has a name, given as a Named: a pipeline's source, each step, and its to. Names label the program's nodes in its description, as Named, Consumed and Produced names do in Java Kafka Streams. A step that keeps a store also takes the store's name, as Java takes a Named and a Materialized name. Two steps cannot share a name.

Grouping records whose key may have changed, after map, flatMap, selectKey or evalMap, sends them through a repartition topic first. Name it with a Repartition: groupBy always takes one, and groupByKey takes one after such a step. As with Java's Grouped, the step that gives groupBy's records their new key takes the repartition's name.

In the first example, groupBy keys each view by its page, so the views of a page, from every user, are counted together. They go through the repartition topic <application id>-views-by-page-repartition. Choosing the key first with selectKey gives the same counts, with groupByKey naming the repartition:

// The same counts, choosing the key first and naming the repartition when grouping
import cats.effect.IO

import xkafka.*
import xkafka.streams.*

def viewsPerPage(input: Topic, output: Topic): Pipeline[IO] =
  val user  = Serde.utf8[IO]
  val page  = Serde.utf8[IO]
  KStream(Named("page-views"), input, user, page)
    .selectKey(Named("by-page"))((_, viewed) => viewed)    // Key each view by its page
    .groupByKey(Repartition("views-by-page"), page, page)  // The key changed, so this takes a Repartition
    .count(Named("count-views"), Store("views-per-page"))
    .toStream(Named("view-counts"))
    .to(Named("write-view-counts"), output, page, Serde.long[IO])

Without the Repartition, this does not compile: the views of a page must reach one partition before they can be counted together. A stream's type says whether its records are keyed as they were read, so the compiler knows which groupByKey applies. KStream(...) and filter, filterNot, mapValues, flatMapValues, peek, evalFilter and evalMapValues after it keep the key as read, and groupByKey(key, value) groups the records where they are. After map, flatMap, selectKey or evalMap, only groupByKey(repartition, key, value) compiles. Each fails to compile where the other applies, with a message saying which to use.

The stream's Keying type member carries this: KeyState.AsRead or KeyState.Changed. Types are inferred, so a program rarely names it. To annotate a stream without losing it, use KStream.Of, as in KStream.Of[IO, String, String, KeyState.AsRead]. A KStream.Unkeyed[IO, String, String] is a stream read from a topic whose type does not say how it is keyed, and it is taken to have changed its key: grouping it by key takes a Repartition, and if its key had not changed after all, Topology.of refuses the name with TopologyError.UnusedRepartition.

repartition sends records through a repartition topic whenever you ask, whether or not their key has changed. Afterwards they are keyed as read from that topic, so groupByKey needs no name for them.

foreach runs an effect for each record, and runs it again for records processed again, such as after a crash, as peek does. print writes each record as [label]: key, value to the Console[F] in scope, labelled with the name of the step before it unless you give a label, or with its own name if it starts a flow. Java's print writes the same lines.

The application's own topics are named after its id: a store's changelog is <application id>-<store>-changelog, and a repartition topic is <application id>-<name>-repartition. The broker creates them when the application first starts.

Topology.of checks the program and reports every problem at once, such as two stores or steps with the same name, or one topic read twice. liftTo raises them in F as an InvalidTopology, and refused settings as an InvalidStreamsSettings.

Steps that see the whole record

filter, mapValues and the steps like them see a record's key and value. To read or change its headers or time, or see where it was read from, use a step that is given the whole record:

// Drop test orders, and put the tenant named in a header into each order's value
import cats.effect.IO

import xkafka.*
import xkafka.streams.*

def tenantOrders(orders: Topic, output: Topic): Pipeline[IO] =
  val id   = Serde.utf8[IO]
  val item = Serde.utf8[IO]
  KStream(Named("orders"), orders, id, item)
    .filterRecord(Named("real-orders"))(_.headers.getAll("x-test").isEmpty)  // Test orders carry an x-test header
    .mapRecordValue(Named("with-tenant")): record =>
      val tenant = record.headers.get[String]("tenant").flatMap(_.toOption).getOrElse("unknown")  // Read the tenant header, or use unknown if it is missing or unreadable
      record.withValue(s"$tenant: ${record.value}").withHeaders(record.headers.remove("tenant"))  // Change the value and headers
    .to(Named("write-orders"), output, id, item)
To Use With an effect
Keep some records filterRecord evalFilterRecord
Act on each record and leave it as it is peekRecord
Change the value, time or headers mapRecordValue evalMapRecordValue
Change those or the key mapRecord evalMapRecord
Make any number of records, keeping the key flatMapRecordValue
Make any number of records, with any key flatMapRecord

Each is given a Record, or a FixedKeyRecord where the key cannot change, as a processor is. withValue and withKey keep the record's time and headers, and withTimestamp and withHeaders change them. record.origin gives the topic, partition and offset the record was read from. See Headers for reading and changing headers.

Grouping or joining after mapRecord, evalMapRecord or flatMapRecord needs a repartition topic, as it does after map. The other steps keep the key.

To make any number of records with an effect, or to use a store, write a processor. If some members run Java Kafka Streams, write these steps in the Java program as process where the key can change and processValues where it cannot, under the same names.

Choosing partitions

By default, each record goes to the partition Kafka's producers choose for its key, so all of a key's records are in one partition, in order. A Partitioner chooses some other way. You can give one in three places:

Where What you can give
to partitioner, which chooses each record's partition in the output topic
repartition partitions, how many the repartition topic has, and partitioner
KTable(...), read from a topic partitioner, saying how that topic is partitioned 
// Keep each region's orders together: through a repartition topic of twelve partitions, then to the output, both partitioned by region.
// An order's key starts with its region, as in "eu-1042".
import cats.effect.IO

import xkafka.*
import xkafka.streams.*

def ordersByRegion(orders: Topic, output: Topic): Pipeline[IO] =
  val text   = Serde.utf8[IO]
  val region = Partitioner.byKey((key: String, count: Int) => Math.floorMod(key.takeWhile(_ != '-').hashCode, count))  // The same region, the same partition
  KStream(Named("orders"), orders, text, text)
    .repartition(Repartition("orders-by-region"), text, text, partitions = Some(12), partitioner = Some(region))      // Twelve partitions, by region
    .to(Named("write-orders"), output, text, text, Some(region))                                                   // The output is partitioned by region too

Without partitions, the broker chooses how many partitions a repartition topic has, as it does for every repartition topic. A count under one is refused when you call Topology.of.

Writing a partitioner

A partitioner is given a record's key, value and headers, and how many partitions the topic has. It gives back a partition, from 0 up to one less than that number. Any other number stops the application, with an error naming the topic.

// Two partitioners: one that goes by the key alone, and one that also reads a header
import xkafka.*
import xkafka.streams.*

// Customers' ids are numbers after a letter, as in "c42": spread customers by that number, each customer always in the same partition
val byCustomer = Partitioner.byKey((key: String, count: Int) => Math.floorMod(key.drop(1).toIntOption.getOrElse(0), count))

// Records with the header priority=urgent go to partition 0, and the rest are spread by key over the other partitions
val urgentFirst = Partitioner[String, String]: (key, _, headers, count) =>
  val urgent = headers.get[String]("priority").contains(Right("urgent"))
  if urgent || count == 1 then 0 else 1 + Math.floorMod(key.hashCode, count - 1)
  • Use Partitioner.byKey when the key alone decides, and Partitioner(...) when the value or headers do too.
  • Only records in the same partition stay in order, so a partitioner that does not go by the key alone can put one key's records out of order.
  • Give the same answer for the same record every time. Records processed again, such as after a crash, should land where they did before.
  • hashCode can be negative: Math.floorMod, unlike %, always gives a number from 0 up.

Java partitioners (JVM only)

On the JVM, a StreamPartitioner written for Java Kafka Streams can be used as a partitioner. It comes with the xkafka-streams-java module, which also depends on Java Kafka Streams:

libraryDependencies += "io.github.pmbmegalom" %% "xkafka-streams-java" % "0.7.1"
// Turn a StreamPartitioner your Java Kafka Streams application already uses into a partitioner for xkafka
import org.apache.kafka.streams.processor.StreamPartitioner

import xkafka.streams.*
import xkafka.streams.interop.*                                       // Adds Partitioner.fromJava, on the JVM only

def sameAsJava(java: StreamPartitioner[String, String]): Partitioner[String, String] = Partitioner.fromJava(java)

It is given each record's topic, key, value, headers and partition count, as in Java. Where it chooses no partition, the record goes where Kafka's default puts it. Where it chooses several partitions, or an empty set, the application stops with an error naming the topic, since xkafka sends each record to one partition.

Tables whose topic is partitioned its own way

A table's topic may be written by another application that partitions it its own way. Give the table that partitioner, made with Partitioner.byKey, since a table needs each key to stay in one partition whatever its value. xkafka then uses it whenever it sends records to be looked up in that table: a stream joined with the table after the stream's key changed, and a foreign-key join looking up the table's rows. Without it, those records go to partitions that do not hold their keys, and find nothing.

With Java members

If some members run Java Kafka Streams, give them a StreamPartitioner that chooses the same partitions, in Produced, Repartitioned, and a foreign-key join's TableJoined. Java has no way to repartition a stream joined with a table by the table's partitioner, so an application with Java members cannot rely on that.

Describing a program

describe shows what a program will run: the topics it reads and writes, the order of its steps, the stores each step uses, and where a repartition divides it. It needs no broker, so a program can be printed or checked in a test before it runs. Here is the first example's:

// Build the first example's program, and describe it
import cats.effect.IO

import xkafka.*
import xkafka.streams.*

val described =
  for
    input    <- Topic.from("page-views").toOption
    output   <- Topic.from("views-per-page").toOption
    topology <- Topology.of(
                  KStream(Named("page-views"), input, Serde.utf8[IO], Serde.utf8[IO])
                    .groupBy(Repartition("views-by-page"), Serde.utf8[IO], Serde.utf8[IO])((_, viewed) => viewed)
                    .count(Named("count-views"), Store("views-per-page"))
                    .toStream(Named("view-counts"))
                    .to(Named("write-view-counts"), output, Serde.utf8[IO], Serde.long[IO])
                ).toOption
  yield topology.describe  // Describing a program needs no broker
// Print the description
described.foreach(println)
// Topologies:
//    Sub-topology: 0
//     Source: page-views (topics: [page-views])
//       --> views-by-page
//     Processor: views-by-page (stores: [])
//       --> views-by-page-repartition-filter
//       <-- page-views
//     Processor: views-by-page-repartition-filter (stores: [])
//       --> views-by-page-repartition-sink
//       <-- views-by-page
//     Sink: views-by-page-repartition-sink (topic: views-by-page-repartition)
//       <-- views-by-page-repartition-filter
// 
//   Sub-topology: 1
//     Source: views-by-page-repartition-source (topics: [views-by-page-repartition])
//       --> count-views
//     Processor: count-views (stores: [views-per-page])
//       --> view-counts
//       <-- views-by-page-repartition-source
//     Processor: view-counts (stores: [])
//       --> write-view-counts
//       <-- count-views
//     Sink: write-view-counts (topic: views-per-page)
//       <-- view-counts
// 
//

Each sub-topology is a part of the program that runs as tasks of its own, and a repartition topic joins two of them: here the first writes views-by-page-repartition and the second reads it. --> points to the nodes a node passes its records to, and <-- to the nodes it gets them from.

Each step appears under its name. A repartition adds the nodes that write and read its topic, named after it. The topic is shown without the application's id, so on the broker this one is <application id>-views-by-page-repartition.

Java Kafka Streams' Topology.describe writes the same text for the same program, which lets you compare the two when moving a program between them.
