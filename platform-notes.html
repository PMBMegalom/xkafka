Platform notes

The API is the same everywhere. These are the places the runtimes differ.

Record delivery

On every platform a consumer joins its group and takes its share of the partitions as soon as it is acquired, even before anything reads its records. A partition whose buffer fills is paused until its reader catches up, so a slow partition does not hold up the others.

A consumer whose records go unread for longer than its maxPollInterval leaves its group. See Group membership.

On the JVM each consumer uses one thread of its own.

Scala Native

The Native backend needs librdkafka 2.16.0, the release xkafka is built and tested with. Older releases lack calls xkafka makes, so an application linked against one, such as Ubuntu 24.04's own librdkafka 2.3.0, does not compile. Confluent publishes each release for Debian and Ubuntu. On Ubuntu 24.04:

sudo mkdir -p /etc/apt/keyrings
curl -fsSL https://packages.confluent.io/clients/deb/archive.key | sudo gpg --dearmor -o /etc/apt/keyrings/confluent-clients.gpg
echo "deb [signed-by=/etc/apt/keyrings/confluent-clients.gpg] https://packages.confluent.io/clients/deb $(lsb_release -cs) main" | sudo tee /etc/apt/sources.list.d/confluent-clients.list
sudo apt-get update
sudo apt-get install librdkafka-dev=2.16.0-1.cflt~ubu24 librdkafka1=2.16.0-1.cflt~ubu24

The librdkafka the Native backend expects is built with TLS, SASL SCRAM and OAUTHBEARER, and every compression codec, so it can reach authenticated brokers and read and write records in any compression.

librdkafka links these against system libraries, so any application linking the Native backend needs OpenSSL, zlib, and zstd available: libssl-dev, zlib1g-dev, and libzstd-dev on Debian and Ubuntu, or brew install openssl@3 zstd zlib on macOS. Homebrew keeps them keg-only, so on macOS their locations have to be named when linking.

Linking an application

Published Native artifacts contain the C glue code and request -lrdkafka. Applications with librdkafka installed in standard compiler and linker locations need no additional xkafka settings. For a nonstandard installation:

nativeConfig := nativeConfig.value
  .withCompileOptions(_ :+ "-I/path/to/librdkafka/include")
  .withLinkingOptions(_ :+ "-L/path/to/librdkafka/lib")

Linking the static librdkafka.a also needs the libraries it was built against, named in this order:

nativeConfig := nativeConfig.value
  .withCompileOptions(_ :+ "-I/path/to/librdkafka/include")
  .withLinkingOptions(_ ++ Seq(
    "-L/path/to/librdkafka/lib", "-lrdkafka", "-lssl", "-lcrypto", "-lz", "-lzstd"
  ))

On macOS add a -L for the OpenSSL installation as well.

Scala.js

The backend is librdkafka, the same release Scala Native uses. It runs on Node.js, not in browsers.

The library comes from npm as @xkafka/librdkafka, which sbt-scalajs-bundler installs. npm adds the prebuilt library for the platform it runs on:

Platform Package
macOS on Apple silicon @xkafka/librdkafka-darwin-arm64
macOS on Intel @xkafka/librdkafka-darwin-x64
Linux x64 with glibc @xkafka/librdkafka-linux-x64-gnu
Linux arm64 with glibc @xkafka/librdkafka-linux-arm64-gnu
Linux x64 with musl, such as Alpine @xkafka/librdkafka-linux-x64-musl
Linux arm64 with musl @xkafka/librdkafka-linux-arm64-musl

Nothing else needs installing: each library carries its own OpenSSL, zlib and zstd. Each xkafka release needs the exact @xkafka/librdkafka version it was published with, so do not pin or override that package. With any other version, acquiring a client fails with a BackendFailure naming both versions.

Transformations

Serializers, deserializers, producer, transactional producer, and consumer settings, offset committers, committable offsets, batches, and records, partition record streams, consumers, and administration clients have cats-tagless FunctorK instances. KafkaProducer has mapK, which needs a Functor for the target effect, and so no FunctorK instance. KafkaClient.imapK transforms a complete client between effects in both directions while preserving Resource cancellation semantics.
